## 解释与复现

验证器在固定候选上全部回答 `valid`，没有完成无效路径诊断；生成与修复模型还存在重复动作、越界等失败。loss 下降及适配器成功加载不能证明规划能力提升。该版本保留为负结果，不替换已验证的逐步 Harness。

候选修复和从零生成后的端到端修复使用不同输入，不能合并宣称规划提升。开发集候选指标使用含 candidate 的 160 条记录，包含验证与修复任务；端到端按网格去重为 191 个。ID／OOD 各 200 条，是既有测试集的再次使用。两者规划网格配对，仅固定候选错误不同；四种端到端流程不读取这些固定候选，所以两组端到端输出一致，不能当作独立网格重复验证。没有根据测试结果重新选择模型或训练参数。

新方案同时改变了任务训练结构和适配方法，不能将与旧多任务基线的差异单独归因于 LoRA。原始指标、逐条候选、四种流程日志和案例保存在 `outputs/gvr/evaluation/<split>/`；权重位于 `outputs/gvr/<stage>/train/best/`。

本次使用保留在 `outputs/gvr/config.json` 与 `outputs/gvr/protocol.json` 的配置，命令见 [GVR 协议](gvr_protocol.md)。发布版默认不声明本地证据已齐备。历史 manifest 路径泛化造成的指纹差异已记录，未改写历史实验报告。

同一批 test_id 固定候选上，旧多任务主模型的验证 Macro-F1 为 0.7141、修复成功率为 19.0%；新方案分别为 0.3333、12.0%。

同一批 test_ood 固定候选上，旧多任务主模型的验证 Macro-F1 为 0.7700、修复成功率为 7.0%；新方案分别为 0.3333、6.0%。

开发集使用默认 CPU 线程设置；两组测试设置 `OMP_NUM_THREADS=1`、`MKL_NUM_THREADS=1`，减少小张量调度开销。正式训练和完整评测均设置 `HF_HUB_OFFLINE=1` 使用完整本地模型缓存。模型权重与解码参数未变；跨 split 的耗时不作速度对照。

共用 GPU 占用账本：本轮增加 1.319 小时，累计 1.859／20 小时；保留了原始历史记录。

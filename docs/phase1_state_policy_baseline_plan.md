## 1. 本轮固定的研究范围

三种模型使用同样的状态动作表示，分别从原始预训练权重全量微调：

| 模型 | 指定 checkpoint | 用途 |
| --- | --- | --- |
| Flan-T5-small | `google/flan-t5-small` | 完整ID基线比较 |
| Flan-T5-base | `google/flan-t5-base` | 完整ID基线比较 |
| BART-base | `facebook/bart-base` | 完整ID基线比较 |

准确revision在试跑前查询并冻结。本轮不直接续训历史 `planning_v3/multi`，避免三模型训练预算及数据经历不一致。历史85%等结果仅为参考，不填入新实验表。仓库历史campaign曾使用 `google-t5/t5-base`，它不是用户本次指定的Flan-T5-base，不能复用该条配置冒充。

主线只保留三个流程：

1. **直接生成**：逐步选择动作，输出完整动作序列，不进行修复。
2. **模型自验证＋固定规则修复**：生成后由同一checkpoint预测验证结果，根据该反馈触发一次共同的修复算法。
3. **执行器验证＋同一规则修复**：生成后由执行器提供诊断，其余修复算法与预算相同。

验证来源由实验配置预先固定，不由模型路由或临时选择。模型验证、执行器验证是两个实验条件；每个验证器都要输出有效性、首次错误位置和类型。

本轮暂不启用S路径缩短、立即折返限制、访问次数约束、束搜索、A*、PPO、迭代多轮修复或新增网格尺寸。原L的局部桥接可作为修复算法基础，但需按第5节改成明确依赖传入反馈的接口。

### 直接生成的精确定义

- 输入采用与当前策略一致的状态文本：地图、当前位置、目标、相对方向、局部合法性信息。三模型完全一致。
- 模型在四个动作之间评分；不在解码时屏蔽越界或撞障碍动作，也不排除重访。
- 从原始起点连续生成，最多36步；到达目标立即结束。选择到非法动作时，将该动作保留在原始输出中并结束该条生成，记为失败，不能丢掉非法动作后报告可行。
- 不做任何后处理即构成直接生成基线。
- “无动作屏蔽”仍有四动作接口与程序构造的状态提示，不宣称是无任何辅助的单次整路径文本生成。

### 2.3 隔离规则

1. 先按障碍布局分组划分，再构造状态、候选和错误。相同布局换起终点仍不能跨train/dev/test。
2. 重算layout_id，核对source_id、样本ID、真实地图内容与重复行；保留派生关系和分割清单。相同训练环境跨任务复用可接受，跨划分复用不可接受。
3. BFS标签计算分别在各自划分内完成。训练只消费训练行的输入与监督目标；开发答案只评分，测试答案只在冻结后评分。预测输入不带optimal_actions、target_plan、gold verdict或最短距离。
4. 关键状态优先采样仅用于训练；不得根据开发/测试失败轨迹补训练样例。开发集不加入优化器、不用于继续训练。
5. 每轮开发集规划从该环境原始起点执行完整路径，不只评估单步标签。缓存完整路径指标和逐例输出。
6. 主模型、checkpoint、提示、预算、反馈格式、修复规则全部在测试前冻结，测试结果不用于回头选模或更改配置。

### 2.4 开发集完整路径评估口径

当前200条开发记录共包含191个唯一 `(layout,start,goal)` 环境。计划固定这些191个环境作为完整路径开发评测视图：只使用已经存在的开发地图，不另采有监督开发样例。100个状态动作样例用于单步诊断，100条验证候选用于验证评测。三个模型、每个epoch使用完全相同的191个规划环境。

历史98个开发环境来自仅对验证行去重，属于不同评测视图。新计划使用191环境时必须新建记录，不能直接与旧98环境的百分比作同样本比较。

### 2.5 历史复用的边界

现有测试集已经用于历史失败分析，不能称为从未看过的盲测。采用旧划分跑第一阶段时，统一标记 `reused_exploratory`；本轮做到没有训练/开发/测试内容交叉、没有用本轮测试选模，但不倒签“从未用过测试”。

如需确认性最终结论，先从未用于任何历史训练、选模或失败分析的布局池中，按预先声明规则建立新的ID/OOD配对holdout，仍遵守各200的正式测试配额。先审计是否存在合格布局，不承诺现已有足够未使用数据；不得把已使用的训练布局重划为“新测试”。这不阻碍先建立清楚的探索性基线。

## 3. 三模型微调与开发集选模

### 3.1 统一学习目标

- 生成任务：保留当前 `optimal_actions` 监督，提高所有最优下一步动作的总概率。
- 验证任务：文本交叉熵，学习 `valid` 或 `invalid | step=… | reason=…`。
- 两类损失均先按样例归一化，再合并平均；同一checkpoint承担状态动作预测和模型验证。不使用强化学习奖励。
- 三模型使用相同训练ID、任务比例、状态提示、允许动作标签、seed和样本呈现次数。

### 3.2 必须先解决的BART适配

现有 `NeuralPolicy` 假设四个动作均为单token，并直接读取首个解码位置；该契约只验证过Flan-T5，不能直接假定BART可用。

试跑前逐模型检查动作分词、前导空格、BOS/EOS、decoder_start_token、教师强制时的动作预测位置；训练损失与推理评分必须对齐同一位置。若某tokenizer把动作拆成多个token，则按完整动作串的条件对数概率评分，并在四个动作候选之间归一化构造同义损失，记录长度处理规则，不能偷偷只取第一个子token。避免因此引入某一模型专用的规划约束或新分类头。

用可人工检查的固定状态验证：目标动作能获得正确loss；训练与推理动作排名一致；不能因BART先预测BOS而误读出“四动作评分”。

### 3.3 初始训练协议

- 从各自原始预训练checkpoint开始，全参数微调。
- seed=42、AdamW、学习率1e-4、weight decay=0.01、正式训练2轮、有效batch=16。
- 默认沿用float32；根据实际GPU显存，允许缩小microbatch并增加梯度累积，保持有效batch不变，必要时启用gradient checkpointing。精度等如需更改，在正式三模型训练前统一冻结并披露。
- 输入不静默截断；固定输入预算并在pilot核验，超长必须显式处理。
- 每个模型只做一个有界pilot，pilot权重不作为正式初始化；pilot部分遍历＋正式两轮不超过约定的三轮上限。
- 不先假定可用的是作业表中的4090。执行时检测实际GPU，测各模型峰值显存、吞吐量和预计总时长；继续累计已有20 GPU小时共享账本，不重置已有用量，异常和pilot也计入。

计划运行全部三个模型，不因“至少两个”的最低要求擅自省略第三个；资源若不足，先报告实测缺口与具体调整选项，不静默换成LoRA或删模型。

### 3.4 选checkpoint与主模型

每个epoch评估全部固定开发环境的完整路径，以及开发验证候选。预先固定排序：

1. **完整路径成功率**优先。
2. 相同则比较验证Macro-F1。
3. 再相同则比较完整路径最优率。
4. 同模型epoch仍相同则保留较早epoch；跨模型完全相同优先较小模型。

训练/开发loss、单步动作准确率和验证首错联合准确率作为诊断完整记录，不再只用loss或单步98%选主模型。先为每个模型选checkpoint，再用相同规则选主模型；不在测试后改规则。

## 4. 验证模块：格式、类型与预测质量

固定两个接口，实验配置明确选择：

```text
model_verify(grid, plan)    -> 同一微调checkpoint的原始验证文本
executor_verify(grid, plan) -> 确定性结构化诊断
```

两者都要能表示四类错误：

| reason | 含义 |
| --- | --- |
| obstacle_collision | 第一次撞障碍 |
| out_of_bounds | 第一次越界 |
| invalid_action_token | 第一次出现非四动作词 |
| goal_not_reached | 动作执行完仍未到目标 |

步骤从1计数；未到目标以 `len(actions)+1` 作为EOS失败位置。执行按时间顺序取首次错误，不因后面还有未知动作词而覆盖较早的碰撞。

数据层检查四类标签及格式；预测层检查模型是否产生这些类别、混淆矩阵、每类召回、格式合法率、Macro-F1、首错定位和类型/步骤联合准确率。格式非法与漏报不能从分母删除。

官方执行器用于真实成功/碰撞等语义核验；原项目对未知动作词的忽略行为与作业要求不同，保留严格词表扩展并明确记录，不把该扩展冒充上游原生行为。

另外，在模型自己生成的路径上报告误接受率和误拒绝率，因为固定受扰动候选上的好成绩不保证模型能验证自己的输出。四动作生成接口不会自然产生未知token，但固定错误候选集必须保留该类，以检验验证/修复模块。

## 5. 修复模块与三条线的可比性

### 5.1 首轮选用共同的规则修复，不再加入额外模型

推荐先做一个**诊断驱动的有界局部修复器**。理由是：不增加训练数据，不引入第二套历史权重，两个反馈来源可在同一修复算法上比较。旧修复模型保留作后续可选对照，首轮不混用；若以后启用，必须核对其训练来源没有与本轮开发/测试重叠。

建议接口：

```text
repair(grid, candidate, supplied_feedback, rollback=2, bridge=3)
    -> repaired_plan | unresolved
```

处理逻辑先冻结：

1. `valid`不触发修复，即使事后评分发现模型误接受，也不能暗中改用执行器反馈。
2. `invalid`必须满足格式、类型和步数边界。格式错误或无法使用的反馈记录为失败，保留原候选，不回填真实诊断。
3. 根据传入的首错步骤 `t`，尝试保留前 `t-1` 个动作；`goal_not_reached`应指向EOS，保留原候选。
4. 对该指定前缀做可执行性检查。若模型声称的前缀本身非法，返回未解决；不另找真实首错位置替换它。
5. 从合法的指定前缀末端开始，最多回退2步，每个锚点最多桥接3步到目标。仅接受合法且到达目标的结果；找不到则返回未解决。

这里的物理合法性检查与有限搜索是两组共有的规则修复能力，并不是额外给模型自验证组提供正确首错文本。误报的步数会影响锚点及可修复范围，必须完整记录。首轮按上述方案主要使用反馈的有效性/首错位置，错误类型用于语义检查；不宣称证明了自然语言诊断措辞或所有类型文本都带来收益。

**必须修改旧L的接口后再接入比较。** 旧 `finish_locally(grid,candidate)` 会重新执行完整候选并取真实首错，如果原封不动放到“模型自验证”之后，会抹去模型诊断错误的影响。这种做法只能研究模型门控，不能声称比较了两种诊断指导修复。

### 5.2 三条线的冻结逻辑

| 条件 | 初始路径 | 验证来源 | 修复 |
| --- | --- | --- | --- |
| Direct | 同一批逐步生成 | 不参与决策，最终仅评分 | 无 |
| Self-Verify + Rule-Repair | 同一初始路径 | 当前checkpoint自己的验证输出 | 共同规则，最多一次 |
| Executor-Verify + Rule-Repair | 同一初始路径 | 执行器诊断 | 同一规则，最多一次 |

Self一行不命名为“模型自己生成修复文本”，因为修复实际由规则完成。两修复条件同预算，无S缩短，无迭代，不用正确答案决定是否调用模型验证。全量原始候选、验证文本、解析结果、触发原因、修复输入输出和最终评分落盘。

每个模型只生成一批初始路径供三组共享。跨模型可复用地图和输入，不能复用其他模型的路径或评分缓存。推理计时分别记录模型前向、共享缓存与规则操作，避免把共享结果重复计费或误当独立样本。

## 6. 评测矩阵与验收

### 6.1 运行顺序

先完成三模型训练及开发选模；在开发集跑通三流程并冻结规则和代码；之后才开始测试。

| 阶段 | 模型 | 数据与内容 |
| --- | --- | --- |
| 开发与选模 | 三个模型 | 每epoch完整规划＋固定候选验证；选择checkpoint和主模型 |
| 开发流程检查 | 三个模型 | 三条线、四种错误、模型误接受/错误步数/非法格式边界 |
| ID基线 | 三个模型 | 三条线端到端；固定候选验证与无效候选修复 |
| OOD完整评估 | 开发集选定主模型 | 双错误候选验证/修复；完整三流程；与ID配对比较 |
| 后续改进 | 主模型 | 根据开发失败案例选择一项想法，再做聚焦消融 |

ID/OOD共享网格时，生成和从该生成开始的端到端三流程只计算一套，不伪造两次独立规划测试。错误数量泛化通过两套不同候选的验证与修复评测体现。

### 6.2 必须报告的指标

- 规划与最终路径：Success、Feasibility、Optimality，均以全部环境为分母。
- 验证：Macro-F1、首错定位、类型准确率、联合准确率、格式合法率及四类分组计数。
- 固定候选修复：所有金标无效候选作为分母，包括被模型误接受、未触发修复的样例；另列“实际触发后的修复率”，不能拿它替代主指标。
- 自生成失败修复：分母为该模型最初生成失败的环境，与固定候选修复率分开。
- 模型误拒绝有效候选后造成的退化、额外调用数、规则搜索预算、GPU记账。
- 至少两个完整案例，含地图、原始候选、真实/模型反馈、修复过程及最终状态。优先包含一个成功案例和一个误诊/修复失败案例。

空错误类别标为N/A并报告n，不伪造0分；可行率100%不等于成功率100%。规则验证器和真实标签共用执行语义时，其一致性成绩作为实现核验，不当作模型学习收益。

## 7. 实施阶段与简洁代码安排

不删除历史工作树、模型和报告，建立单一新入口，旧实验不作为运行依赖。拟新增 `state_baselines/`，保留少量职责明确文件：

| 文件职责 | 处理内容 |
| --- | --- |
| `protocol.json` | 三checkpoint、数据版本、预算、选模规则、反馈来源 |
| `data.py` | 固定数据读取、完整路径开发视图、隔离与配额审计 |
| `model.py` | 模型token契约、状态动作评分、验证文本、两任务损失 |
| `workflow.py` | 三条线与诊断驱动的共同修复器 |
| `run.py` | audit / pilot / train / select / evaluate分阶段入口 |
| `report.py` | 原始轨迹复核、指标表与报告 |

地图语义与执行器复用已核对的核心实现，不复制历史大量Harness开关。边界测试覆盖：三模型动作位置一致性；无动作屏蔽不偷偷选第二合法动作；四错误与EOS；Self误接受不修复；错误诊断不被真实标签替换；两条件修复预算一致；训练/开发/测试隔离及冻结检查。

阶段交付顺序：

1. **数据审计与冻结草案**：来源、ID、重复、实际布局交集、四类覆盖、191开发环境视图。
2. **CPU流程与token契约**：三个接口、共同修复、针对反馈边界的测试。
3. **GPU pilot**：准确checkpoint、前向与梯度、验证输出、显存和三模型预计资源。
4. **三模型正式微调与开发选择**：每epoch保存完整路径结果；落盘 `selection.json`。
5. **测试前冻结**：数据、权重、源码、提示、修复参数与选择证据哈希。
6. **ID三模型＋主模型OOD**：逐例结果、指标、资源、案例报告，完成第一部分。

运行产物固定包括：`dataset_audit.json`、`training.json`、`dev_metrics.json`、`selection.json`、`freeze.json`、`traces.jsonl`、`metrics.json`、`gpu_ledger.json`、`report.md`。数据库层面使用现有JSONL样例＋manifest＋结构化结果即可，无需另建数据库服务。

## 8. 什么时候开始探索改进

基线跑完后，根据开发集失败分布选方向：若主要是两点循环，再测试立即折返规则；若主要是验证误接受，优先改验证；若诊断正确但局部修复预算不足，再研究修复。不得预设立即折返一定是新三模型的主要问题，也不根据本轮测试结果反复挑最高分改进。

这份计划的首要交付是可信的第一部分：**同一数据上的三模型无动作屏蔽规划，明确的两种验证来源，同一修复算法，开发集完整路径选模，以及可复核的三条基线。**

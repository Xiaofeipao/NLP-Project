## 静态检查中修正的问题

- 历史 pilot 校验没有包含 LoRA r／alpha／dropout，修改适配器设置后仍可能沿用旧 pilot。现增加训练签名，同时锁定阶段目标、学习率和选模方式。旧 pilot 没有签名时拒绝用于新的正式训练，须在独立输出目录重新准备。
- `verify` 原先完成模型加载与开发集推理后才拒绝覆盖已有文件。现在在导入 CUDA 与构造模型之前检查 verify／evaluate 的输出路径，评测还会提前检查输入文件和官方执行器。
- 审计原先容许额外的陌生网格混入 pipeline 文件。现要求全部保存网格属于冻结 split，同时保留历史开发集 191 个网格记录的兼容性；评分仍只选指定的 40 个 Generate 网格。

## 根据真实结果准备的候选

历史验证器对 ID／OOD 候选全部判 `valid`，但 token loss 仍下降；候选修复为 12%／6%，端到端均为 0%。这些结果不足以确认单一失败原因，以下只是待验证假设。

`config.gvr.next.json` 为独立、默认关闭训练证据位的候选配置，输出到 `outputs/gvr_next/`。原 `config.gvr.json` 继续使用原 token 平均损失和开发集 loss 选模，不更改历史模型、数据、产物或已发布指标。

- Verify：每个样本的有效 token 损失先按长度归一化，再对样本求平均；额外加入首个判别 token 的交叉熵，权重为 1。运行时先检查 valid／invalid 的首 token 确实不同，后续步骤、原因、EOS 仍正常监督。这是加强类别判断信号的尝试，不能保证消除单一类别预测。
- V／R 的候选学习率为 `1e-3`，G 沿用 `1e-4`。这是假设值，尚无实测依据证明优于原值；阶段覆盖值和实际学习率均写入报告。仍限制每阶段两轮，复用原 4,000 条训练记录及共用账本。
- Verify 按开发集 Macro-F1、首错定位、失败类型准确率、负 loss 的字典序选 checkpoint；G／R 按开发集成功率、最优率、负 loss 选择。由此避免只因 teacher-forcing loss 更低就选中任务指标更差的 epoch。报告记录最佳 epoch、排序值与每轮诊断。
- 测试集不参与选权重；本轮配置修改依据既有失败现象，后续复用 ID／OOD 的结果应标明探索性质，不能视为全新盲测或单因素 LoRA 因果证据。

没有增加搜索兜底或禁止连续同方向动作：合法最短路本来可能包含多次 left／right。本轮实际结果表明，生成重复与端到端失败仍未解决。

## 预备检查与执行顺序

CPU 回归测试已执行，覆盖损失对 padding 的屏蔽与梯度、任务指标优先选模、配置拒绝、pilot 签名、输出覆盖保护和外来网格审计。运行中另加快照替换的暂时失败重试、永久失败保留证据和其他 IO 错误直接抛出的测试。再次运行前仍须按 [GVR 协议](gvr_protocol.md) 核对证据和剩余账本，不直接开启默认训练证据位。

候选的 pilot／train 使用 `--protocol config.gvr.next.json`，按 G → V → R 顺序分别准备 fresh pilot 和正式训练。使用该新协议时，G 从固定预训练版本开始训练，不能混用原 G 的权重或旧 pilot。验证和评测同样使用新协议并选择新输出路径。阶段目标、LoRA 或训练参数变化后需要重新做匹配的 pilot。

实现集中在 `ppnl/gvr_objectives.py`、`ppnl/gvr_training.py`、`ppnl/gvr_audit.py` 与 `scripts/run_gvr.py`；`ppnl/harness.py` 增加了快照替换的有限重试。完整报告、机器可读指标、候选配置与对应代码一同发布；新一轮权重、运行配置快照、源码快照及完整日志仍保存在本地 `outputs/gvr_next/`，此次未上传这些大体积运行产物。

# 固定多任务权重后的 Harness 与消融

## 1. 本轮目标与边界

这次整理统一了已有执行器、模型适配器、会话状态机和指标的调用方式。固定历史开发集选出的 Flan-T5-small 多任务全量微调 checkpoint，重新运行后处理与消融，不增加训练。课程原要求的两模型比较、训练数据构造与开发集选模证据见 [Project 6 整理](project6_overview.md)。

主流程是：**一个共享 G/V/R checkpoint → 显式方法配置 → 配对推理 → 统一评分与成本记录**。逐步 policy、LoRA 和 RL 属于使用其他训练产物的独立研究，保留实现和历史证据，不混入本轮固定权重比较。

验收要求：全量 dev、ID、OOD；自验证不得接收金标反馈；明确所有指标分母；记录首错分组和逐条修复轨迹；同一环境共用初始 G；支持相同身份断点恢复；代码、模型、数据或方法变化时拒绝复用旧结果；真实 GPU 运行与账本留痕。

## 3. V、执行器与 R 的边界

**V 是学习式诊断任务**，输入网格和候选，输出 `valid` 或 `invalid | step=... | reason=...`。预测可能错误。`self` 由 V 决定是否修复，R 接收模型反馈；执行器只在流程结束后评分，因此误判 valid 会原样接受失败路径。

**执行器是确定性程序**，提供碰撞、越界、非法 token、未达目标的首错诊断。executor 方法用它控制停止和产生 R 的反馈，运行期间不调用模型 V。独立 V 测试仍对全部候选执行，用于报告三任务中验证能力的实际水平。

实际控制顺序比 `G→V→R` 简写更完整。self 先运行 V：预测 `valid` 就停止，否则 R 修复一次，再调用 V 检查新候选；第二次 V 仍判无效时因修复轮数已满而结束。格式不合法的 V 输出也进入修复分支，不被替换成金标。executor_one/three 每轮先获取执行器反馈，成功就停止，否则在剩余轮数内调用 R，再检查新候选。任一修复结果与历史候选相同（按空白规范化比较）会立即停止，因此不一定发生最后一次 V/执行器检查；最终成功与否另由评分器确定。

从 G 开始且未发生后端失败重试时，self 最多使用 G×1、V×2、R×1；executor_one 最多 G×1、R×1、执行器诊断×2；executor_three 最多 G×1、R×3、执行器诊断×4。固定候选实验直接以给定候选开始，不实际调用 G。独立候选 V 的调用属于诊断评测成本，不能算成每个 executor 方法在推理时使用了 V。

R 重新生成整条路径，不保证只修改错误位置，也不天然保留合法前缀。`none`/`generic` 只删减传给 R 的反馈文本，执行器仍负责是否修复及停止。C4 还会在解码每一步使用执行状态，因此去掉反馈文本并不等于去掉执行器。

严格执行器只承认空白分隔的四动作。`valid` 表示动作全合法且最终到达目标；合法但停在目标外是 feasible、invalid。首错从 1 开始计数，合法序列未达目标的失败步是动作数 + 1。官方 `is_goal` 核对合法 token 路径的成功/碰撞语义，详细首错与严格 token 检查由本地扩展提供。

## 4. 消融回答什么问题

配置中 13 个名字与实际处理一一对应。下表的修复次数是上限，执行器已确认成功时不会调用 R；除 self 外，模型 V 均不参与这些方法的运行决策。

| 配置名 | 修复控制 | R 或替代器 | 传给 R 的反馈 |
| --- | --- | --- | --- |
| `direct` | 不修复 | 无 | 无 |
| `self` | 模型 V 门控，最多 1 次 | 同一 checkpoint 的普通贪心 R | 模型 V 原文 |
| `executor_one` | 执行器门控，最多 1 次 | 普通贪心 R | 完整执行器诊断 |
| `executor_three` | 执行器门控，最多 3 次 | 普通贪心 R | 每轮完整执行器诊断 |
| `syntax_beam`（B4） | 执行器门控，最多 1 次 | 四动作/EOS 束搜索 | 完整执行器诊断 |
| `constrained`（C4） | 执行器门控，最多 1 次 | B4 加状态约束 | 完整执行器诊断 |
| `backtrack` | 执行器门控，最多 1 次 | C4 加丢弃分支恢复 | 完整执行器诊断 |
| `constrained_none` | 执行器门控，最多 1 次 | C4 | 空反馈文本 |
| `constrained_generic` | 执行器门控，最多 1 次 | C4 | 通用无效提示 |
| `backtrack_none` | 执行器门控，最多 1 次 | 带回溯的 C4 | 空反馈文本 |
| `backtrack_generic` | 执行器门控，最多 1 次 | 带回溯的 C4 | 通用无效提示 |
| `uniform` | 执行器门控，最多 1 次 | 等权动作评分的约束束搜索 | 不读取反馈文本 |
| `manhattan` | 执行器门控，最多 1 次 | 长度优先、累计 Manhattan 距离评分的约束束搜索 | 不读取反馈文本 |

本轮保留的比较各有一个明确问题：

| 对比 | 改变的处理 | 能回答的问题 |
| --- | --- | --- |
| direct → self | 增加模型 V 门控与一次 R | 学到的诊断是否能帮助生成路径 |
| self → executor_one | 反馈改为确定性执行器 | 诊断错误是否限制修复 |
| executor_one → executor_three | 最多一次改为三次修复 | 迭代是否有收益；重复候选会提前停止 |
| ordinary → B4 | R 改成四动作/EOS 的 beam=4 | 格式限制与搜索本身贡献多少 |
| B4 → C4 | 增加合法转移、禁止重访、仅目标可 EOS | 状态约束贡献多少 |
| C4 → backtrack | 保留丢弃分支，活动束耗尽时恢复 | 在相同评分行数上限下能否减少失败 |
| original → none/generic | 去掉详细首错文本或替换为泛化提示 | R 是否真正利用细粒度诊断 |
| C4 → uniform/manhattan | 移除神经评分，保留同类约束搜索 | 成功来自学习模型还是规则搜索 |

回溯消融需同时报告实际评分行数、处理 token 与时间：共同上限不代表实际算力相等。B4 到 EOS 仅表示解码完成，不代表路径成功。C4 按模型序列分数排序，不保证最短路；禁止重访也不能保证找到目标。规则对照不调用微调 R，不能把其结果写成模型修复能力。

默认共 13 个配置；none/generic 分别在 C4 和 backtrack 上运行。ordinary→B4 同时改变动作语法、束宽和动作预算，是方法对照；B4→C4 才是在同一搜索预算下移除/加入状态约束的聚焦消融。没有把每个比较都解释成单因素因果证明。

具体预算为 beam width 4、最多 36 个动作、每次搜索最多评分 148 个前缀；EOS 也需要一次前缀评分。普通 G/V/R 使用贪心文本生成，沿用模型配置的最多 128 个新增 token，不能将其预算称为 36 个动作。每个持久化方法会话最多 8 次控制器请求、300 秒累计活动时间；控制器请求包含从缓存取出的初始 G 和规则请求，实际神经调用另计。

none 保留网格与候选，只将 `Feedback:` 后的诊断文本置空；generic 改为 `The candidate is invalid. Find a valid path.`。uniform 对每个动作赋 -1、EOS 赋 0；manhattan 对每步使用负的长度惩罚及目标距离，长度惩罚足够大使路径长度优先。二者都保留有限束宽与预算，不是 BFS/A*，也没有完备性保证。端到端规则对照仍使用共享的模型 G，仅移除了修复搜索中的神经评分。

## 5. 数据、指标与结果产物

开发集固定 G 40 / V 100 / R 60；每个测试集 V 200 / R 100 / G 200。R 的分母仅包括金标无效候选。候选 self 使用模型反馈；候选 executor 使用严格执行器反馈，original 对应给定正确诊断的修复能力。direct 在候选表中表示原样保留无效候选的零修复对照。

ID 和 OOD 使用相同网格/起终点，只改变预置候选的错误数。它们的 V/R 分别运行；初始 G 与其后续 planning 会话只运行一次，共享给两个 split。不能将两份相同端到端成绩当作 400 个独立环境。

Success = 全路径合法且最终到达目标；feasibility = 全部动作合法；optimality = 成功且动作数等于 BFS 最短路。三者都以全部被评路径为分母。V 报告 Macro-F1、首错定位、类型及联合准确率。错误分组按执行时**实际首错**，区别于替换/删除等注入操作。

首错定位分母为全部无效候选，要求模型预测 invalid 且步号正确；类型准确率只要求 invalid 和类型正确，联合准确率要求步号、类型均正确。某一错误类型子集只有 invalid 类，此时沿用二分类 Macro-F1 会使全对的上限也只有 0.5。因此错误分组主要看样本数、定位、类型、联合准确率和修复成功率，总体 Macro-F1 才用于比较整体 V 能力。

`protocol.json` 在推理前冻结模型、源码、数据、配置和运行库；各 split 保存 `results.json`、验证/生成/候选轨迹，底层会话保存日志和候选历史。共享初始 G、方法逻辑成本和实际物理执行量分开记录；普通文本生成未暴露 decoder 内部计数时，零值表示未统计，而不是免费。

每个方法的 `executor_calls` 仅统计控制循环获取诊断的次数，不含数据标签核对、流程后的 `OfficialOracle` 评分、BFS 指标计算或每个解码动作的约束判断。规则搜索的前缀数记为 `rule_search_rows`，神经解码前缀数记为 `decoder_row_steps`；模型请求、token 与符号工作量不能混为一列。`active_seconds` 是方法内调用的活动墙钟，GPU ledger 是占用设备期间的总墙钟，包含模型加载及其间的 CPU 工作，不代表 GPU 满负荷计算时间。

顶层 `physical_cost` 将相同环境的 G 与后续方法会话只累计一次，各 split 的方法表仍展示相同配对任务成本，不能再相加作为总耗费。`case_studies.json` 提供最多 10 条候选的全部方法历史和最终执行轨迹，详细解释见本轮报告。

本轮先固定整张方法矩阵，再按默认 dev→ID→OOD 顺序运行，不依据本轮 dev 或 test 成绩删除或改选方法。测试开始时的 receipt 记录已完成 dev 报告的摘要；显式 test-only 运行则记录空值，不冒称存在本轮开发证据。历史主 checkpoint 的开发集选择与本轮矩阵冻结是两项不同证据。

这些测试集已在历史研究中查看过，本轮属于固定方案复跑及探索性消融。协议冻结防止运行中途换方案，不能将已用过的测试集重新变成未见测试集。

## 6. 运行与恢复

```powershell
python scripts/run_post_training.py preflight --spec configs/post_training.json
python scripts/run_post_training.py run --spec configs/post_training.json --out outputs/post_training/run_001
python scripts/run_post_training.py run --spec configs/post_training.json --out outputs/post_training/run_001 --resume
```

运行环境需安装项目依赖、恢复历史全量权重并获取官方执行器。跨机器可显式覆盖 checkpoint、dataset、executor、ledger 路径。不要为续跑修改原协议；更改任何方法、预算或数据后使用新输出目录。GPU 账本沿用已有历史，运行目录分离不代表重新获得预算。

本轮 GPU 结果及代码核查记录见 [已完成的复跑报告](post_training_run_20261112.md)，含 13 个配置的全部指标、成本及逐例分析。
